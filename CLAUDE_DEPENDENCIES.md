# DEPENDENCIES ON THE CLAUDE PRODUCT — what the method assumes
### Survey of 31 October 2026 · to be re-read at every version of the package

*The method relies on functions of the Claude product (the app, its projects, its sessions, its tools). They can
change, without the package knowing: **this survey ages**. It dates from 31 October 2026; every new version of the
package re-reads it line by line and corrects its date. It only describes what the package uses: each line points to
the place that uses it.*

**If a function changes or disappears**: find its line; read what breaks and the fallback; apply the fallback while you
correct the package (templates, skill, `3_GITHUB.md`) in a “Package vN” commit, then your project's method at its next
version (`GUIDE.md` §7). Do not work around it in silence: a rule that relied on the function is rewritten or removed.

| the function | what the method does with it | where the package uses it | what breaks if it changes or is missing | the fallback |
|---|---|---|---|---|
| **The claude.ai projects**: instructions, documents, mirror of the living docs | the instructions carry your profile and pointers; the living docs and the references written once are kept there in folders; at every close-out the PL copies each modified file over with `project_write` and `local_path`, from its clone | `GUIDE.md` §2 (layer 2) and §4; `1_PROJECT_INSTRUCTIONS.md`; `templates/METHOD.md` §6 (“The living docs”, “Where each document lives”); `skill/SKILL.md` §5 | the sessions no longer find where the living docs are; the mirror goes stale without a sound; a file copied from the text the tool returns is not worth the file | the living-docs repository is the source, the project only holds a mirror: the PL clones the repository and reads the checkpoint there; the PL gives you back the text of the instructions to paste |
| **The sub-agents of the session**: the dev, delegated readings; the choice of model (Opus, Sonnet, Haiku) and of effort | the PL launches the dev (Agent tool, in the background, model and effort from the brief); it may delegate a reading to a light sub-agent, outside its context | `skill/SKILL.md` §5 (circuit of a batch, step 2); `templates/DEV_COMMAND.md` §A; `templates/METHOD.md` §2 (step 2), §3 (effort mode), §6 (the board's fallback) | the PL can no longer launch the dev; the choice of model or effort is no longer offered; a sub-agent consumes the credit of the PL's session | the line you paste into a new conversation, with “Sonnet · Medium · new conversation” above it (`templates/DEV_COMMAND.md` §B); the dev then tells you only one sentence, when it stops or delivers |
| **The artifacts**: publishing a page, the reading required before republishing, the files next to the page, private by default | the workstreams board is published as an artifact, at the same link: the fixed page and its data file together; the page is private until you share the link | `templates/METHOD.md` §6 (“The workstreams board”); `skill/SKILL.md` §7; `templates/living-docs-repo/README.md`; `GUIDE.md` §4 | if the tool requires reading every published file, republishing without reading is refused; if the files next to the page are no longer served, the page shows no board; a page opened from the disk does not load its data | read the page in full before republishing and, if the tool requires reading the data file, the light sub-agent that reads it (method §6); hand the page over as an `.html` file in the discussion; serve it (`python3 -m http.server`) rather than open it from the disk |
| **The attachment of GitHub repositories with write access**: `add_repo`, shallow clone, `fetch` before `push` | each session attaches its repositories, one clone at a time; the PL writes to the living docs with `git pull`, `git fetch origin main` before pushing; a session creates no tag, no release, no branch deletion, no repository: you do | `3_GITHUB.md` §4 and §5; `templates/METHOD.md` §6 and §7; `skill/SKILL.md` §5 (“Session pitfalls”); `templates/CHECKPOINT.md` §1; `2_PL_BOOTSTRAP_PROMPT.md` | a session can no longer clone or push; the safeguard refuses an attachment you have not asked for in so many words; a push from an out-of-date copy is rejected (HTTP 413) | the fixed line names all the domain's repositories, with push access (it stands for your request); failing a repository, a brief that lists the files to upload and a named `.md` report (`skill/SKILL.md` §4, point 5); if a limit falls (tag, release), you can delegate the move |
| **The session identifier in the commits**: the session attribution line | the short id, the baton of a checkpoint, is the last eight characters of this identifier; the arbiter looks for it in the commit messages to judge silence | `templates/METHOD.md` §1a (“The baton”); `skill/SKILL.md` §3; `templates/ARBITER.md` §1.3; `templates/CHECKPOINT.md` | without the attribution line, or with another format, the arbiter no longer finds a session's last commit and flags forgotten sessions that are alive | agree on a mark each PL puts in its commit messages, and name it in place of the identifier (`templates/ARBITER.md` §1.3) |
| **The bridge to the owner's machine**: linked folders, terminal, screen | the PL's session works on your machine itself (a game, an application, the screen); you validate the access in the conversation | `skill/SKILL.md` §5a; `templates/METHOD.md` §1; `templates/LOCAL_RUNNER.md`; `GUIDE.md` §2a (“Your machine”) | the session no longer sees your machine; an access that needs your validation waits while you are away; every workstream that needs the machine stops | the local runner, driven by files (`templates/LOCAL_RUNNER.md`); a workstream that needs the machine stays in debt while you are not there |
| **The scheduled tasks**: creation, time, approval, notifications | the arbiter is a fresh session started every morning; a session resume can be too, by a one-off task; its notifications arrive as a push through the mobile app | `templates/ARBITER.md` §4; `GUIDE.md` §2b; `skill/SKILL.md` §3 (the resume) and §11 | the arbiter no longer runs, nobody sees the whole of the living docs; a run that must wait for an approval stops; without a notification, nothing signals that a run took place | start the arbiter by hand (`templates/ARBITER.md` §4, point 7: the first run is started by hand); without an arbiter, the PL or the coordinator runs the checker at their close-out (`templates/METHOD.md` §6); the log is authoritative, not the notification |
| **The size of the context and its measure**: `context.py`, the session log | the handover is decided on the size of the context at the last turn: warn at 450,000 tokens, hand over at 550,000 at the latest | `templates/context.py`; `skill/SKILL.md` §3; `templates/METHOD.md` §6 (“The handover is measured, not guessed”); `CORE.md` §4 | if the format or the location of the log (`~/.claude/projects/*/*.jsonl`, `usage` field) changes, the script no longer reads or reads wrong; if the context window or its cost changes, the thresholds no longer hold | the saturation signs (losing the thread, contradictions, a forgotten decision): the same handover, right away; every handover notes them, to recalibrate the thresholds on measurements |
| **The personal skill**: the account's skills | `methode-cdp` carries the roles, the posture and the general circuit, for all your projects; it is the installed copy of `skill/SKILL.md` | `GUIDE.md` §2 (layer 1), §3 (point 3) and §7; `skill/SKILL.md` | if personal skills are no longer offered or change shape, the first layer no longer loads: the sessions no longer have the roles or the posture | the project's method (layer 3) already overrides the skill and carries the essentials; the PL clones the package and reads `skill/SKILL.md` at the start of the session (`2_PL_BOOTSTRAP_PROMPT.md` §A) |

*What the method does **not** ask of Claude: the product's memory. The method and the project's state do not live there;
they are in versioned documents a fresh dev can read (`GUIDE.md` §2).*
