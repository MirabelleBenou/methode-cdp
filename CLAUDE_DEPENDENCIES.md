# DEPENDENCIES ON THE CLAUDE PRODUCT — what the method assumes
### Survey of 1 November 2026 · to be re-read at every version of the package

*The method relies on functions of the Claude product (the app, its projects, its sessions, its tools). They can
change, without the package knowing: **this survey ages**. It dates from 1 November 2026; every new version of the
package re-reads it line by line and corrects its date. It only describes what the package uses: each line points to
the place that uses it.*

**If a function changes or disappears**: find its line; read what breaks and the fallback; apply the fallback while you
correct the package (templates, skill, [`3_GITHUB.md`](3_GITHUB.md)) in a “Package vN” commit, then your project's method at its next
version ([`GUIDE.md`](GUIDE.md) §7). Do not work around it in silence: a rule that relied on the function is rewritten or removed.

| **The model name written in full**: “Opus”, “Sonnet”, an effort (“Medium”, “High”) | the brief and the fallback line name the model and effort as the app offers them; the dev's defaults are in the table of figures | `templates/METHOD.md` §6 (“The method's figures”) and §3; [`templates/BRIEF.md`](templates/BRIEF.md) (header); `templates/DEV_COMMAND.md` §B | a model renamed or withdrawn, an effort that changes label: the brief names something that can no longer be found | the PL tells the owner the closest model, and corrects the method's table of figures at the next package |
| **The artifacts**: publishing a page, the reading required before republishing, the files next to the page, private by default | the workstreams board is published as an artifact, at the same link: the fixed page and its data file together; the page is private as long as you do not share the link | `templates/METHOD.md` §6 (“The workstreams board”); [`templates/living-docs-repo/README.md`](templates/living-docs-repo/README.md); `GUIDE.md` §4 | the tool **requires reading in full any file the session did not write, including the already-published data file being replaced** (a real case: a republish refused until it had been read); if the files next to the page are no longer served, the page no longer shows a board | **the board is republished at close only**, after reading in full the page and its JSON (a data file small enough to be read in full, method §6); hand the page over as an `.html` file in the discussion; serve it (`python3 -m http.server`) rather than open it from the disk |
| **The attachment of GitHub repositories with write access**: `add_repo`, shallow clone, `fetch` before `push` | each session attaches its repositories, one clone at a time; the PL writes to the living docs with `git pull`, `git fetch origin main` before pushing; a session creates no tag, no release, no branch deletion, no repository: you do; **installing the arbiter assumes that a session can push a file under `.github/workflows/`** — a separate right on GitHub's side, granted today | `3_GITHUB.md` §4 and §5 (the pitfalls); `templates/METHOD.md` §6 and §7; [`templates/CHECKPOINT.md`](templates/CHECKPOINT.md) §1; [`2_PL_BOOTSTRAP_PROMPT.md`](2_PL_BOOTSTRAP_PROMPT.md) | a session can no longer clone or push; the safeguard refuses an attachment you have not asked for in so many words; **a push from a shallow clone that has not run `fetch` sends the whole tree, which the proxy refuses for its size (HTTP 413) — it is not a fast-forward refusal** | `git fetch origin main` before `git push`; the fixed line names all the domain's repositories, with push access (it stands for your request); failing a repository, a brief that lists the files to upload and a named `.md` report (`templates/METHOD.md` §3, “It carries”); if a limit falls (tag, release), you can delegate the move; **if the right to write under `.github/workflows/` is missing, you copy the arbiter's workflow yourself** (`templates/ARBITER.md` §4) |
| **The session identifier in the commits**: the session attribution line | the short id, the baton of a checkpoint, is the last eight characters of this identifier; the arbiter looks for it in the commit messages to judge silence | `templates/METHOD.md` §6 (“The baton”); [`templates/ARBITER.md`](templates/ARBITER.md) §1.4; `templates/CHECKPOINT.md` | without the attribution line, or with another format, the arbiter no longer finds a session's last commit and flags forgotten sessions that are alive | agree on a mark each PL puts in its commit messages, and name it in place of the identifier (`templates/ARBITER.md` §1.4) |
| **The bridge to the owner's machine**: linked folders, terminal, screen | the PL's session works on your machine itself (a game, an application, the screen); you validate the access in the conversation | `templates/METHOD.md` §1; [`templates/LOCAL_RUNNER.md`](templates/LOCAL_RUNNER.md); `GUIDE.md` §2a (“Your machine”) | the session no longer sees your machine; an access that needs your validation waits while you are away; every workstream that needs the machine stops | the local runner, driven by files (`templates/LOCAL_RUNNER.md`); a workstream that needs the machine stays in debt while you are not there |
| **The scheduled tasks**: creation, time, **automatic approval**, notifications | the controller is a fresh session started every Monday; a session resumption can be too, by a one-off task; its notifications arrive as a push in the mobile app | [`templates/CONTROLLER.md`](templates/CONTROLLER.md) §4; `GUIDE.md` §2b; `templates/METHOD.md` §6 (the resumption) | **without automatic approval, nobody is there to approve**: the task stops at the first move to approve; without a notification, nothing says a run took place | set the automatic approval in the task's settings, if the organization allows it; run the controller by hand; the log is authoritative, not the notification |
| **The scheduled GitHub Actions**: `schedule`, `workflow_dispatch`, `contents: write`, the e-mail of a failed workflow | the arbiter is a daily GitHub Action, with no session or model token; it commits and pushes as `github-actions[bot]`, and **fails when it has filed a workstream**: GitHub's e-mail is the signal | `templates/ARBITER.md` §0, §4; `templates/living-docs-repo/arbiter.yml`; `GUIDE.md` §2b; `templates/METHOD.md` §6 | the arbiter no longer runs or no longer pushes (write right withdrawn, branch rule on a protected repository); without the failure e-mail, nothing warns that it has filed | run the action by hand (“Run workflow”); without an arbiter, the PL or the coordinator runs the checker at its close-out (`templates/METHOD.md` §6); the log is authoritative, not the e-mail |
| **The context window and its measure**: `context.py`, the session log | the handover is decided on the size of the context at the last turn; the thresholds (`templates/METHOD.md` §6, their only source) **are counted above the fixed load** measured at the first turn and **assume a window size**, which the same table gives; **the fixed load is the platform's** (system instructions, native tools, memory, project instructions): unplugging the connectors only reduces it by about 1% (method §6), the saving is to be sought in what the sessions read | `templates/context.py`; `skill/SKILL.md` §4; `templates/METHOD.md` §6 (“The handover is measured”); [`CORE.md`](CORE.md) §4 | if the format or location of the log (`~/.claude/projects/*/*.jsonl`, `usage` field) changes, the script no longer reads or reads wrong; if the fixed load changes with the platform, it is measured and recalibrates itself (`context.py`, method §6); if the window or its cost changes, the table no longer holds | the saturation signs (lost thread, contradictions, a forgotten decision): same handover, right away; every handover notes them, to recalibrate the thresholds on measures |
| **The automatic compaction of the conversation** | the product may summarize the conversation itself when it nears its limit | `templates/METHOD.md` §6 (“The handover is measured”); `templates/context.py` (the “compaction seen” line) | **the most likely risk**: `context.py` then measures a reduced context, the threshold never arrives and the PL goes on over a summary, without knowing it | the measure at three moments (each closed batch, before each dev launch, every ten exchanges), the handover at a natural end of the queue without waiting for the threshold, and the mark `context.py` writes when it sees a compaction |
| **The sessions' sandbox**: paths, per-command timeout, nothing durable | each session starts from a new disk and rebuilds everything from the repositories; a command has a timeout (up to 600 s, to be observed); a background process is stopped at the end | `templates/METHOD.md` §7 (“General”); `templates/DEV_PROMPT.md` §1, §2; `templates/DEV_COMMAND.md` §A | a state kept on the disk disappears; a long command is cut; a process left running skews the next measure | everything is rebuilt from the repositories; a long command goes to the background with a witness file; the dev prompt forbids leaving a process running |
| **The usage limits**: the session's credit, the per-period caps | a dev, a review and the PL's session consume the same credit; a limit reached cuts the session | `templates/METHOD.md` §2 (the dev pushes at every step), §8 (the target cost); `templates/ARBITER.md` §4 | the PL's or the dev's session stops in the middle of a batch; a scheduled task can fail | **the dev pushes its branch at every step**: a new session resumes from the branch; offset the time of scheduled tasks; an isolated failure is not made up, the next run checks everything |
| **The fallback by a conversation opened by hand** *(fragile)* | when the PL cannot launch a sub-agent, you paste a line into a new conversation of the project, with the model and effort above it | `templates/DEV_COMMAND.md` §B; `templates/METHOD.md` §2 (“Fallback”) | the conversation may fail to attach a private repository; the dev only talks to the PL through what it pushes and a sentence to you | **next fallback**: a brief that lists the files to upload and a named `.md` report (`templates/METHOD.md` §3, “It carries”) |
| **The personal skill**: the account's skills | `methode-cdp` carries what a session knows before reading the project's method (roles, posture, start), for all your projects; it is the installed copy of `skill/SKILL.md` | `GUIDE.md` §2 (layer 1) and §7; `CORE.md` §2; `skill/SKILL.md` | if personal skills are no longer offered or change shape, the first layer no longer loads: the sessions no longer have the roles or the posture | the project's method (layer 3) already overrides the skill and carries the essentials; the PL clones the package and reads `skill/SKILL.md` at the start of the session (`2_PL_BOOTSTRAP_PROMPT.md` §A) |

*What the method does **not** ask of Claude: the product's memory. The method and the project's state do not live there;
they are in versioned documents a fresh dev can read (`GUIDE.md` §2).*
