# DÉPENDANCES AU PRODUIT CLAUDE — ce que la méthode suppose
### Relevé du 31 octobre 2026 · à relire à chaque version du package

*La méthode s'appuie sur des fonctions du produit Claude (l'application, ses projets, ses sessions, ses outils). Elles
peuvent changer, sans que le package le sache : **ce relevé vieillit**. Il date du 31 octobre 2026 ; chaque nouvelle
version du package le relit ligne à ligne et corrige sa date. Il ne décrit que ce que le package emploie : chaque ligne
renvoie à l'endroit qui s'en sert.*

**Si une fonction change ou disparaît** : repère sa ligne ; lis ce qui casse et le repli ; applique le repli le temps de
corriger le package (modèles, skill, `3_GITHUB.md`) dans un commit « Package vN », puis la méthode de ton projet à sa
prochaine version (`LISEZ_MOI.md` §7). Ne contourne pas en silence : une règle qui s'appuyait sur la fonction se réécrit
ou se retire.

| la fonction | ce que la méthode en fait | où le package s'en sert | ce qui casse si elle change ou manque | le repli |
|---|---|---|---|---|
| **Les projets claude.ai** : instructions, documents, miroir des vivants | les instructions portent ton profil et des pointeurs ; les vivants et les références écrites une fois y sont rangés en dossiers ; à chaque clôture le CdP recopie chaque fichier modifié par `project_write` avec `local_path`, depuis son clone | `LISEZ_MOI.md` §2 (couche 2) et §4 ; `1_INSTRUCTIONS_PROJET.md` ; `modeles/METHODE.md` §6 (« Les vivants », « Où vit chaque document ») ; `skill/SKILL.md` §5 | les sessions ne retrouvent plus où sont les vivants ; le miroir se périme sans bruit ; un fichier recopié depuis le texte que rend l'outil ne vaut pas le fichier | le dépôt des vivants est la source, le projet n'en porte qu'un miroir : le CdP clone le dépôt et lit le checkpoint là ; le CdP te redonne le texte des instructions à coller |
| **Les sous-agents de la session** : le dev, les lectures déléguées ; le choix du modèle (Opus, Sonnet, Haiku) et de l'effort | le CdP lance le dev (outil Agent, en arrière-plan, modèle et effort du cadrage) ; il peut déléguer une lecture à un sous-agent léger, hors de son contexte | `skill/SKILL.md` §5 (circuit d'un lot, étape 2) ; `modeles/COMMANDE_DEV.md` §A ; `modeles/METHODE.md` §2 (étape 2), §3 (mode d'effort), §6 (le repli du tableau) | le CdP ne peut plus lancer le dev ; le choix du modèle ou de l'effort n'est plus offert ; un sous-agent consomme le crédit de la session du CdP | la ligne que tu colles dans une conversation neuve, avec « Sonnet · Medium · conversation neuve » au-dessus (`modeles/COMMANDE_DEV.md` §B) ; le dev ne te dit alors qu'une phrase, quand il s'arrête ou livre |
| **Les artefacts** : publier une page, la lecture exigée avant de republier, les fichiers à côté de la page, privés par défaut | le tableau des chantiers se publie en artefact, au même lien : la page fixe et son fichier de données ensemble ; la page est privée tant que tu ne partages pas le lien | `modeles/METHODE.md` §6 (« Le tableau des chantiers ») ; `skill/SKILL.md` §7 ; `modeles/depot-vivants/README.md` ; `LISEZ_MOI.md` §4 | si l'outil exige de lire chaque fichier publié, la republication sans lecture est refusée ; si les fichiers à côté de la page ne sont plus servis, la page n'affiche plus de tableau ; une page ouverte depuis le disque ne charge pas ses données | lire la page en entier avant de republier, et, si l'outil exige la lecture du fichier de données, le sous-agent léger qui le lit (méthode §6) ; remettre la page en fichier `.html` dans la discussion ; la servir (`python3 -m http.server`) plutôt que l'ouvrir depuis le disque |
| **Le rattachement des dépôts GitHub en écriture** : `add_repo`, clone peu profond, `fetch` avant `push` | chaque session rattache ses dépôts, un clone à la fois ; le CdP écrit aux vivants par `git pull`, `git fetch origin main` avant de pousser ; une session ne pose ni tag, ni release, ni suppression de branche, ni création de dépôt : tu les fais | `3_GITHUB.md` §4 et §5 ; `modeles/METHODE.md` §6 et §7 ; `skill/SKILL.md` §5 (« Pièges des sessions ») ; `modeles/CHECKPOINT.md` §1 ; `2_PROMPT_AMORCAGE_CDP.md` | une session ne peut plus cloner ni pousser ; le garde-fou refuse un rattachement que tu n'as pas demandé en toutes lettres ; un push d'une copie pas à jour est rejeté (HTTP 413) | la ligne fixe nomme tous les dépôts du domaine, en accès push (elle vaut ta demande) ; à défaut de dépôt, un cadrage qui liste les fichiers à téléverser et un rapport en `.md` nommé (`skill/SKILL.md` §4, point 5) ; si une limite tombe (tag, release), tu peux déléguer le geste |
| **L'identifiant de session dans les commits** : la ligne d'attribution de session | l'identifiant court, le témoin d'un checkpoint, est les huit derniers caractères de cet identifiant ; l'arbitre le cherche dans les messages de commit pour juger le silence | `modeles/METHODE.md` §1 bis (« Le témoin ») ; `skill/SKILL.md` §3 ; `modeles/ARBITRE.md` §1.3 ; `modeles/CHECKPOINT.md` | sans la ligne d'attribution, ou avec un autre format, l'arbitre ne retrouve plus le dernier commit d'une session et signale des sessions oubliées qui vivent | convenir d'une marque que chaque CdP met dans ses messages de commit, et la nommer à la place de l'identifiant (`modeles/ARBITRE.md` §1.3) |
| **Le pont vers la machine du porteur** : dossiers reliés, terminal, écran | la session du CdP travaille elle-même sur ta machine (un jeu, une application, l'écran) ; tu valides l'accès dans la conversation | `skill/SKILL.md` §5 bis ; `modeles/METHODE.md` §1 ; `modeles/EXECUTANT_LOCAL.md` ; `LISEZ_MOI.md` §2 bis (« Ta machine ») | la session ne voit plus ta machine ; un accès qui demande ta validation attend quand tu es loin ; tout chantier qui a besoin de la machine s'arrête | l'exécutant local, piloté par fichiers (`modeles/EXECUTANT_LOCAL.md`) ; un chantier qui demande la machine reste en dette tant que tu n'y es pas |
| **Les tâches planifiées** : création, heure, approbation, notifications | l'arbitre est une session neuve lancée chaque matin ; une reprise de session peut l'être aussi, par une tâche unique ; ses notifications arrivent en push par l'application mobile | `modeles/ARBITRE.md` §4 ; `LISEZ_MOI.md` §2 ter ; `skill/SKILL.md` §3 (la reprise) et §11 | l'arbitre ne tourne plus, personne ne voit l'ensemble des vivants ; un passage qui doit attendre une approbation s'arrête ; sans notification, rien ne signale qu'un passage a eu lieu | lancer l'arbitre à la main (`modeles/ARBITRE.md` §4, point 7 : le premier passage se lance à la main) ; sans arbitre, le CdP ou le coordinateur lance le vérificateur à sa clôture (`modeles/METHODE.md` §6) ; le journal fait foi, pas la notification |
| **La taille du contexte et sa mesure** : `contexte.py`, le journal de session | la passation se décide sur la taille du contexte au dernier tour : prévenir à 450 000 jetons, passer la main à 550 000 au plus tard | `modeles/contexte.py` ; `skill/SKILL.md` §3 ; `modeles/METHODE.md` §6 (« La passation se mesure ») ; `NOYAU.md` §4 | si le format ou l'emplacement du journal (`~/.claude/projects/*/*.jsonl`, champ `usage`) change, le script ne lit plus ou lit faux ; si la fenêtre de contexte ou son coût change, les seuils ne valent plus | les signes de saturation (pertes de fil, contradictions, une décision oubliée) : même passation, tout de suite ; chaque passation les note, pour recalibrer les seuils sur des mesures |
| **La skill personnelle** : les skills du compte | `methode-cdp` porte les rôles, la posture et le circuit général, pour tous tes projets ; elle est la copie installée de `skill/SKILL.md` | `LISEZ_MOI.md` §2 (couche 1), §3 (point 3) et §7 ; `skill/SKILL.md` | si les skills personnelles ne sont plus offertes ou changent de forme, la première couche ne se charge plus : les sessions n'ont plus les rôles ni la posture | la méthode du projet (couche 3) prime déjà sur la skill et porte l'essentiel ; le CdP clone le package et lit `skill/SKILL.md` en début de session (`2_PROMPT_AMORCAGE_CDP.md` §A) |

*Ce que la méthode **ne** demande **pas** à Claude : la mémoire du produit. La méthode et l'état du projet n'y vivent
pas ; ils sont dans des documents versionnés qu'un dev neuf peut lire (`LISEZ_MOI.md` §2).*
